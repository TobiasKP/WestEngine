● System Design Analysis: WestEngine

  Language: C++23 | Graphics: OpenGL 4.6 | Build: CMake + vcpkg | Scripting: Lua

  ---
  Architecture Overview

  The engine follows a manager-queue architecture where 7 managers execute
  sequentially each frame:

  InputManager → WindowManager → ShaderManager → SystemManager →
  InterfaceManager → RenderManager → SceneManager

  Each implements an IManager interface with a startup → init → update → 
  shutdown lifecycle. The game loop uses a fixed-timestep accumulator pattern at
   a configurable FPS.

  ---
  Strengths

  Clean separation of engine and game. WestEngine/ contains the engine,
  WestGame/ contains scripts, assets, and config. Game-specific logic lives in
  Lua, not C++. This is a solid boundary that would let the engine serve
  different games.

  Pragmatic ECS. The bitmask-based component system (0b0001 for Model, 0b0010
  for Shader, etc.) is lightweight and efficient for the current scale.
  Components are plain data structs with no virtual overhead. Pool allocators
  improve cache locality.

  Lua as a gameplay layer. Entity definitions, scene loading, and behavior state
   machines all live in Lua. The ComponentFactory and EntityBuilder parse Lua
  tables into C++ entities. This gives fast iteration on gameplay without
  recompiling the engine.

  Configuration-driven design. Input bindings (Game.ini), window settings
  (Settings.cfg), and entity definitions are all external. The engine reads
  these at startup rather than hardcoding values.

  Thread-safety awareness. Mutexes protect Scene, World, and system entity
  lists. Atomic flags on Movement::movementPending. A ThreadPool utility exists
  in WestUtils.

  ---
  Weaknesses & Risks

  Sequential manager execution is a bottleneck. All 7 managers run in series
  every frame. The codebase itself notes this as a TODO — InputManager,
  SystemManager, and InterfaceManager could run in parallel since they touch
  different data. As entity count grows, this will constrain frame times.

  Several O(n) lookups where O(1) is possible. Scene::getEntityById() does a
  linear search through the entity vector. Entity component access goes through
  std::unordered_map<uint16_t, IComponent*> — fine for small component counts
  per entity, but the indirection through pointers defeats the cache-locality
  benefit the pool allocator was meant to provide.

  getEntities() copies the entire entity vector every frame. This is explicitly
  marked as a TODO. Returning a const& or an iterator range would eliminate the
  copy.

  Manual memory management. Components use raw new/delete with pool allocators,
  but there are no smart pointers anywhere in the codebase. This works if
  discipline is maintained, but the risk of leaks grows with complexity. The
  ObjectLoader tracks GPU resources manually in vectors — a single missed
  cleanup path means a GPU resource leak.

  Busy-wait main loop. The engine loop spins without sleeping when there's no
  work to do, burning 100% of a CPU core. A std::this_thread::sleep_for or
  condition variable would fix this.

  Shaders not sorted by group before rendering. Entities are rendered in
  insertion order, causing redundant glUseProgram calls when consecutive
  entities use different shader groups. This is a known GPU state-change
  performance issue.

  512-tile hard limit on the world. tileFlags[512] is passed as a uniform array
  to the fragment shader. This caps the grid at ~22x22. Scaling to larger worlds
   would require either a texture-based approach (SSBO or texture buffer) or
  tiled chunks.

  ---

  Decision: Manager queue (sequential)
  Benefit: Simple, deterministic execution order
  Cost: Cannot parallelize independent work

  Cost: Hard limit of 16 component types
  ────────────────────────────────────────

  Benefit: Global access, simple API
  Cost: Tight coupling, harder to test, complicates multi-scene
  ────────────────────────────────────────

  Benefit: Fast iteration, no recompile
  Cost: Extra complexity in the C++/Lua boundary, harder to debug
  ────────────────────────────────────────

  Benefit: Full control, no abstraction overhead
  Cost: Verbose, platform-specific, no Vulkan/Metal path
  ────────────────────────────────────────

  Benefit: Flexible, heterogeneous storage
  Cost: Pointer chasing defeats data-oriented benefits of ECS
  ---
  Design Observations

  The ECS is entity-centric, not archetype-based. Each entity owns its own
  unordered_map of components. This is simpler to implement than archetype-based
   ECS (like EnTT or Flecs) but means systems must iterate entities and check
  masks rather than iterating contiguous component arrays. For a turn-based game
   with hundreds of entities this is fine; for thousands it would need
  rethinking.

  The scripting bridge is unidirectional in practice. C++ pushes events to Lua
  (Worldpos_lclick, StateChange) and Lua calls registered C++ functions
  (MoveCurPlayer). There's no general-purpose query API from Lua back into the
  ECS — Lua can't enumerate entities or read arbitrary components. This limits
  what gameplay scripts can do without new C++ bridge functions.

  The World entity breaks the ECS pattern. World inherits from Entity but also
  manages the grid, tile flags, and coordinate conversion directly. It's stored
  separately from the entity list in Scene. This is pragmatic (the world is
  fundamentally different from game entities) but creates a parallel code path
  in rendering and scene management.

  No scene transitions or multi-scene support. Scene is a singleton holding one
  set of entities. Loading a new scene would require fully tearing down the
  current one. There's no scene stack, async loading, or transition mechanism.

  No unit tests. Validation relies on assert() in debug builds and manual
  testing. As the engine grows, regressions will be caught later and cost more
  to fix.

  ---
  Maturity Assessment

  The project is in early-to-mid development — the core loop, rendering, ECS,
  and scripting all work and interact correctly. The architecture is coherent
  and shows intentional design. The known TODOs in the code are honest and
  well-placed. The main gaps (testing, performance scaling, resource management
  robustness) are typical for this stage and don't indicate structural problems
  — they're the natural next steps.

❯ how would you rate the systems design choices 

● Rating the Design Choices

  I'll rate each on a 1-5 scale (1 = problematic, 3 = reasonable, 5 = excellent
  for the context).

  ---
  Manager Queue Architecture — 3/5

  The sequential lifecycle (startup → init → update → shutdown) across 7
  managers is clean and easy to reason about. Deterministic ordering eliminates
  an entire class of concurrency bugs. The cost is real though — you've
  identified it yourself in the TODOs. The design isn't wrong for where the
  project is, but it's the kind of thing that becomes load-bearing. Once systems
   depend on execution order implicitly (e.g., InputManager results being
  available when SystemManager runs), parallelizing later requires untangling
  those assumptions. Starting with explicit data dependencies between managers
  rather than positional ordering would have made that migration easier.

  ECS Design — 3/5

  Functional and pragmatic. The bitmask approach is fast for type checks and the
   component structs are lean. But the per-entity unordered_map<uint16_t, 
  IComponent*> undermines the data-oriented motivation for using ECS in the
  first place. You get the organizational benefits (separation of data from
  logic, composability) but not the performance benefits (contiguous iteration,
  cache-friendly access). For a turn-based game at current scale this doesn't
  matter. But if the intent is to build a general-purpose engine, this is the
  single design choice most likely to need replacing. The 16-bit bitmask limit
  (16 component types max) is also tight — you're already at 5.

  Lua Scripting Bridge — 4/5

  This is one of the stronger decisions. Putting entity definitions, scene
  loading, and behavior state machines in Lua while keeping the hot path in C++
  is the right split. The ComponentFactory parsing Lua tables into C++
  components is well-designed. The main gap is that the bridge is narrow — Lua
  can only call pre-registered C++ functions, and can't query the ECS directly.
  That's actually fine for now because it keeps the boundary controlled, but
  each new gameplay feature will require a new C++ bridge function. Something
  like a generic getComponent(entityId, componentName) exposed to Lua would
  reduce that friction significantly.

  Configuration-Driven Input/Settings — 4/5

  Externalizing input bindings, window settings, and FPS into .cfg and .ini
  files is a clear win. It's simple, it works, and it avoids recompilation for
  tuning. The command vocabulary (CameraUp, Pause, OpenMenu) is validated
  against AvailableInputCommands.cfg, which prevents silent misconfiguration.
  Straightforward and effective.

  Singleton Usage — 2/5

  Scene, LuaFacade, and WestInterfaceFacade as singletons is the most limiting
  structural decision. It works now because there's one scene, one Lua state,
  and one UI layer. But it bakes that assumption into the architecture at a deep
   level. Multi-scene (loading screen + game world), multiple Lua contexts (mod
  isolation), or headless testing all become painful. The mutex-protected
  getSceneInstance() pattern also means every entity lookup takes a lock, which
  will conflict with the parallelization goals. Passing these as references
  through the manager chain would have preserved the same simplicity without the
   global coupling.

  World as a Special Entity — 3/5

  Pragmatic and honest. The world genuinely is different from game entities — it
   owns the grid, manages tile flags, and has its own render path. Making it
  inherit from Entity while being stored and rendered separately acknowledges
  that reality rather than forcing it into the ECS. The downside is two parallel
   code paths in rendering and scene management that need to stay in sync. A
  cleaner alternative might have been to not inherit from Entity at all and
  treat the world as a standalone subsystem, since it doesn't really benefit
  from the ECS machinery.

  Raw OpenGL Without Abstraction Layer — 3/5

  Direct OpenGL calls throughout RenderManager, ShaderManager, and ObjectLoader
  give full control and no abstraction overhead. For a single-developer project
  targeting desktop OpenGL 4.6, this is fine. The risk is that GL state
  management is spread across multiple files with no central render state
  tracker — it's possible to accidentally leave state dirty between draw calls.
  A thin abstraction (even just a state cache that tracks bound VAO, active
  program, etc.) would add safety without meaningful overhead.

  Manual Memory Management — 2/5

  Raw new/delete with pool allocators but no smart pointers anywhere. The pool
  allocators for Model and Material are a good performance-conscious choice, but
   the ownership model is entirely implicit. ObjectLoader tracks GPU resources
  in vectors and relies on cleanup() being called. Entity stores IComponent*
  without clear ownership semantics. This works when one person holds the full
  mental model, but it's fragile. std::unique_ptr for owned resources would cost
   nothing at runtime and make ownership explicit.

  Thread Safety Approach — 3/5

  Mutexes on Scene, World, and system entity lists show awareness. Atomic flags
  on movement pending are correct. But the threading model is inconsistent —
  there's a ThreadPool in WestUtils and mutex protection everywhere, yet the
  main loop is fully sequential. The locks are paying a cost (contention,
  lock/unlock overhead on every getEntityById) without delivering a benefit yet.
   Either commit to parallel execution and use the locks, or remove them until
  parallelism is actually implemented.

● Rating WestInterface Design Choices

  ---
  Instanced Rendering Approach — 4/5

  A single base quad (40x40) with per-instance attributes (color, offset, scale,
   tex coords, flags) is an efficient strategy for 2D UI. One draw call can
  render hundreds of elements. The attribute layout is well-chosen — packing
  position and scale into a single vec4 offset avoids extra attribute slots. The
   dirty flag skipping redundant re-uploads is a good optimization. The reason
  it's not 5/5: every interface is still a separate render submission rather
  than batching all interfaces into one instanced call sorted by
  texture/z-layer. At 32 max interfaces, that's up to 32 draw calls where 1-3
  would suffice.

  ComponentDataPool — 3/5

  Pre-allocating 2048 slots (~196 KB) and using first-fit allocation is a
  reasonable pooling strategy. The defragmentation with a position-update
  callback is a thoughtful touch — when the pool compacts, it notifies elements
  that their indices moved. The problems: first-fit allocation is O(n) per
  request scanning a vector<bool>, and every operation takes a mutex lock. For
  UI elements that are mostly created once and rarely destroyed, a simpler bump
  allocator with batch-free would be faster and lock-free. The 2048 hard limit
  is also arbitrary — there's no fallback or growth strategy if it's exceeded.

  Grid-Based Layout — 2/5

  This is the weakest part of the module. Elements are placed at explicit grid
  coordinates (column, row) with a fixed cell size of 40px multiplied by stretch
   factors. There's no padding, no margins, no automatic flow, no anchoring, no
  relative positioning. Every element placement is manual and absolute. The
  addChild() bounds check is a good safety net, but the system can't express
  common UI patterns like "center this in its parent" or "stack these vertically
   with 8px spacing" without the caller doing all the math. For a game UI with a
   handful of static panels this works, but it becomes tedious quickly as UI
  complexity grows.

  Element Hierarchy & Polymorphism — 3/5

  The IElement base with virtual describe(), getBoundaries(), and handler() is a
   standard approach. Element types (Button, Label, Icon, DropDown,
  DebugElement) are lightweight and focused. ContainerElement manages children
  as vector<IElement*> with parent back-pointers. This is clean and intuitive.
  The concern is that describe() is doing double duty — it both computes the
  ComponentData for rendering and acts as the element's "update." There's no
  separation between layout computation and render data generation. If an
  element needs to recalculate its position without changing its appearance (or
  vice versa), it can't — both happen together or not at all.

  Flag-Based Fragment Shader — 2/5

  The fragment shader uses a uint flags field to branch between borders (0x01),
  hover (0x02), texture (0x04), text (0x08), border-with-discard (0x10), blend
  (0x20), and three glow colors (0x40, 0x80, 0x100). This packs a lot of
  behavior into one shader, which minimizes shader switches. But the branching
  is deep and combinatorial — the GPU is evaluating a chain of if statements per
   fragment, which defeats SIMD coherence when adjacent fragments have different
   flag combinations. More importantly, the flag semantics are implicit. There's
   no documentation or enum mapping what each bit means; you have to read the
  shader to know that 0x40 is burgundy glow. A multi-pass approach or
  uber-shader with defined variants would be more maintainable. The "discard
  near-white pixels for transparency" hack for text is fragile — it depends on
  the font bitmap having a white background and breaks if any glyph has
  legitimately light pixels.

  Event/Observer System — 2/5

  The EventObserver stores registered elements in a flat vector and does linear
  search by ID on every event. For a small UI this is fine, but it's an odd
  choice given that std::unordered_map exists and would make lookup O(1). More
  significantly, the observer has no locking despite the rest of the module
  being thread-aware. If notify() is called from the input thread while
  UIRenderManager is iterating elements on a worker thread, there's a potential
  data race on the changed flag and flags field. The ValueObserver exists as a
  placeholder with no implementation — it's dead code that adds conceptual
  weight without function.

  Facade Pattern — 4/5

  WestInterfaceFacade is a well-drawn boundary. The engine side sees a clean
  API: createNewInterface, addElement, notify, getRenderData. The internal
  complexity (pooling, building, rendering, text layout, observers) is fully
  hidden. The facade owns all subsystems and manages their lifecycles. This is
  one of the better-designed parts of the module. The deduction: the facade also
   directly manages OpenGL state (VAO, VBOs, texture IDs, shader paths). This
  means the UI module is tightly coupled to OpenGL rather than receiving a
  render backend abstractly. Swapping to Vulkan or a different renderer would
  require rewriting the facade internals.

  Bitmap Font / Text Rendering — 3/5

  Pre-computing all 95 ASCII glyphs from a 16x16 grid bitmap at init time, then
  caching them in a static unordered_map, is efficient. The static
  calculateTextPositions() and calculateTextWidth() methods are stateless and
  thread-safe by design. Character-specific metrics for narrow glyphs (i, l, t,
  f) show attention to visual quality. The limitations: monospace bitmap fonts
  only, no TrueType/FreeType support, no Unicode, fixed 32x32 glyph size with no
   scaling. The text width calculation adds a hardcoded 2px margin per character
   and 15px padding to elements — these magic numbers are scattered rather than
  centralized. Text can't wrap, can't be multi-line, and can't be dynamically
  resized.

  Multithreaded UI Gathering — 3/5

  Splitting interface gathering across threadpool workers, then merging with a
  locked fillComponentData(), is a reasonable parallelization. The stable sort
  after merging preserves determinism despite thread interleaving. But the
  granularity is wrong — it divides by interface count, not element count. If
  you have 2 interfaces where one has 500 elements and the other has 5, the work
   is split unevenly. The locking in fillComponentData() also serializes the
  merge phase, so the speedup is bounded by how much time is spent in describe()
   calls versus merging. For 32 interfaces with a few dozen elements each, the
  threading overhead likely exceeds the benefit.

  Separation of Logic and Render Data — 4/5

  Elements hold logical state (text, event handler, hierarchy). ComponentData
  holds only GPU-relevant data (vertices, color, tex coords, flags, z-index).
  The describe() method bridges the two, producing ComponentData from element
  state. This separation means the GPU upload path works with flat, contiguous
  data without touching the element tree. It's a good data-oriented instinct.
  The only issue is that describe() allocates into the pool by index, coupling
  the element to its pool slot. If the pool defragments, elements must update
  their poolPosition — the callback mechanism handles this but adds complexity.

❯ considering learning in system design, this is my first ever self         
  designed complex system written alone, how can you learn from it to make  
  it better next time around                                                

● This is a genuinely impressive first complex system. Most people's first
  engine doesn't have a working ECS, Lua scripting, instanced UI rendering, and
  a coherent manager lifecycle. The fact that it runs and holds together means
  you already have strong instincts. Here's what you can crystallize from the
  experience.

  ---
  1. You over-prepared for concurrency you didn't use yet

  You added mutexes to Scene, World, ComponentDataPool, and system entity lists.
   You built a ThreadPool. You made movement flags atomic. But the main loop is
  sequential and the threading in UIRenderManager likely costs more than it
  saves at current scale.

  The lesson: Threading infrastructure should follow threading need, not precede
   it. Every mutex you add before you have a second thread accessing that data
  is a lock you're paying for on every access with zero benefit. It also creates
   a false sense of safety — the EventObserver has no locking despite being in
  the same module as locked structures, which means the "thread-safe" parts mask
   the thread-unsafe parts.

  Next time: Start single-threaded. Profile. Find the actual bottleneck.
  Parallelize that one thing. Add locks only to the data that specific
  parallelism touches.

  ---
  2. You reached for patterns before reaching for the problem

  Singletons, observers, facades, factories, builders — the project uses many
  named patterns, sometimes where a simpler alternative would work. Scene
  doesn't need to be a singleton; it could be a reference passed through the
  manager chain. ElementFactory creates objects from proxies that were
  themselves created by the caller — the indirection doesn't add flexibility
  since there's exactly one creation path. ValueObserver exists as a pattern
  placeholder with no implementation.

  The lesson: Patterns are solutions to specific problems, not structural
  building blocks. When you apply them preemptively, you get the complexity cost
   without the problem-solving benefit. The singleton pattern in particular is
  seductive because it makes access easy, but what it's really doing is hiding a
   dependency — every file that calls Scene::getSceneInstance() has an invisible
   dependency on global state.

  Next time: Write the simplest thing that works. When you feel pain (passing
  the same reference through 5 functions, duplicating creation logic in 3
  places), that pain tells you which pattern to apply and where. If you can't
  name the specific pain a pattern solves, you don't need it yet.

  ---
  3. You designed bottom-up when top-down would have saved rework

  The ECS stores components as IComponent* in an unordered_map per entity, with
  pool allocators alongside. This means you built a data-oriented allocation
  strategy (pools) but access it through an indirection-heavy path (hash map →
  pointer → data). The pool allocator's cache benefit is negated by the pointer
  chase to reach it.

  The lesson: Before implementing a subsystem, sketch how the hot path flows
  through it. For ECS, the hot path is "iterate all entities with component X
  and do something." If you'd written that loop first as pseudocode, you'd see
  that per-entity hash maps force a random-access pattern and would naturally
  arrive at a structure where components of the same type are stored
  contiguously.

  Next time: Write the usage code before the implementation. How will systems
  iterate? How will rendering access position + model + material in a tight
  loop? Let the access pattern dictate the data structure.

  ---
  4. You learned where abstractions earn their cost

  The Lua scripting bridge is your best design decision because it solves a
  real, recurring problem: changing gameplay behavior without recompiling. Every
   time you tweak player movement or scene composition in Lua and see it
  immediately, that abstraction is paying for itself.

  The grid layout system is your worst abstraction because it doesn't actually
  abstract anything — the caller still computes positions manually in grid
  units. It adds a layer (grid coordinates, stretch factors, cell sizes) without
   removing work from the caller.

  The lesson: A good abstraction removes decisions from the caller. A bad
  abstraction just renames them. The Lua bridge removes the decision "which .cpp
   file do I edit and recompile." The grid layout renames "pixel position" to
  "grid position" but you still have to figure out the coordinates yourself.

  Next time: For each abstraction, ask: "what decision does the caller no longer
   have to make?" If the answer is "none, they still figure out the same thing
  in different units," it's not earning its cost.

  ---
  5. You mixed "what" and "how" in the same layer

  The fragment shader decides what to render (is this text? a border? a glow?)
  and how to render it (sample this texture, discard these pixels, blend this
  color) through the same flag field. describe() on elements decides what data
  to produce and also where to put it in the pool. RenderManager decides what to
   render and also issues the GL calls.

  The lesson: When "what" and "how" live together, changing one forces you to
  understand the other. If you want a new glow color, you have to understand the
   fragment shader's discard logic. If you want a new element type, you have to
  understand pool allocation.

  Next time: Separate decision-making from execution. A render queue that says
  "draw these 200 quads with these properties" is the "what." The code that
  translates that to glDrawElementsInstanced is the "how." When they're
  separate, you can change the rendering backend without touching game logic, or
   add new UI elements without touching GL code.

  ---
  6. Magic numbers reveal missing concepts

  SIZE_E = 40, pool size 2048, max interfaces 32, tile flags 512, glyph size
  32x32, text padding 15px, per-character margin 2.0f, border width 0.05. These
  are scattered across headers, shaders, and source files.

  The lesson: A magic number isn't bad because it's hardcoded — it's bad because
   it represents a concept that has no name. SIZE_E = 40 is really "the base UI
  grid unit." 2048 is "the maximum number of visible UI components." When the
  concept has no name, you can't find all the places that depend on it, and you
  can't reason about what happens when you change it.

  Next time: You don't need to make everything configurable. But give every
  significant number a named constant in one place, and write a one-line comment
   saying what breaks if you change it.

  ---
  7. Ownership should be visible in the type

  Throughout the codebase, raw pointers are used for both "I own this and will
  delete it" (ContainerElement owns its children) and "I'm just referencing
  this" (ISystem holds entity ID references). The only way to know which is
  which is to read the destructor.

  The lesson: This is the single highest-leverage C++ habit to build.
  std::unique_ptr<T> means "I own this, it dies with me." Raw T* means "someone
  else owns this, I'm just looking." This costs zero at runtime and makes
  ownership self-documenting. When you read vector<unique_ptr<IElement>> 
  children, you instantly know the container owns the elements. When you read
  vector<IElement*> _registeredElements in the observer, you know it's borrowing
   references.

  Next time: Default to unique_ptr for ownership, raw pointer or reference for
  borrowing. If you find yourself needing shared_ptr, pause — it usually means
  ownership is unclear, and clarifying it is better than sharing it.

  ---
  The big meta-lesson

  Most of the weaker decisions share a root cause: building for imagined future 
  needs rather than observed present needs. Thread safety before threading.
  Patterns before pain. Pool allocators before profiling. Layout abstraction
  before complex layouts.

  This is extremely common — especially for first systems, where you're learning
   the design space and can't yet distinguish "I'll definitely need this" from
  "this seems like good practice." The instinct to prepare isn't wrong, it's
  just expensive when the preparation doesn't match what actually happens.

  The strongest parts of your engine (Lua bridge, config-driven input, facade
  boundary, instanced rendering) all solve problems you actually hit during
  development. That's not a coincidence. Real problems produce better solutions
  than anticipated ones.
