● Great, now I have a thorough understanding of your architecture. Here's my
  brainstorming:

  ---
  Where Does This Logic Belong?

  The short answer: split between engine and game, but the split point matters.

  Engine Side (C++)

  The engine should own the infrastructure — things that are mechanics-agnostic:

  1. World tile query — The World entity already knows its grid. The engine
  should expose a way to ask "which tile is at this world position?" and "give
  me all tiles within radius R of tile X,Y". This is spatial/geometric math, not
   game logic. Think of it as a service the world provides.
  2. Tile hover detection — The engine already does screen-to-world raycasting
  in PositionCalculation::getWorldPosition(). Extending this to snap to the
  nearest tile center is engine-level work. Every frame the mouse moves, the
  engine can compute "hovered tile (x,y)" and expose it.
  3. Tile visual state — The world shader (worldshader.fs) currently draws a
  flat green. The engine should support per-tile color overrides (or at minimum,
   a "highlight set" of tile indices + a color). This is rendering
  infrastructure, not game logic.

  Game Side (Lua)

  The game should own the rules:

  1. Movement radius value — How far can this unit move? That's a game stat.
  Define it in your entity YAML or in Lua logic: movementRange = 5.
  2. Which tiles are reachable — Given the entity's current tile and its
  movement range, compute the set of valid destination tiles. For a flat plane
  with no obstacles, this is a simple Manhattan/Chebyshev distance check. Later
  it becomes pathfinding — but the rule ("can I reach this tile?") is game
  logic.
  3. What happens on click — When the player clicks a highlighted tile, Lua
  decides: "move the entity there" (and later: "spend movement points", "end
  turn", etc.).

  The Communication Flow

  Every frame:
    Engine (C++) → computes hovered tile from mouse pos
                 → passes hovered_tile to Lua callback

    Lua (Game)   → checks if hovered_tile is within movement radius
                 → if yes: tells engine "highlight tile X,Y as DESTINATION"
                 → if no:  tells engine "highlight tile X,Y as OUT_OF_RANGE" (or
   don't highlight)

  On click:
    Engine (C++) → sends clicked_tile to Lua callback

    Lua (Game)   → validates tile is reachable
                 → calls engine API: entity:moveTo(tile_x, tile_y)
                 → tells engine: clear movement radius display

  Concretely, What to Build

  1. Engine: World tile awareness

  Add to the World class or a new utility:
  - worldPosToTile(glm::vec3 worldPos) → (int tileX, int tileY) — converts a
  world position to grid coordinates (just floor(x), floor(z) given your 1-unit
  quads)
  - tileCenterToWorldPos(int x, int y) → glm::vec3 — inverse
  - getTilesInRadius(int cx, int cy, int radius) → vector<pair<int,int>> —
  returns all tiles within range (Chebyshev distance for grid movement, or
  Manhattan if you want diamond shape like XCOM)

  2. Engine: Per-tile highlight rendering

  Two approaches, in order of simplicity:

  - Uniform-based (simpler, fine for now): Pass a small buffer or uniform array
  to the world shader marking which tiles should be highlighted and with what
  color. In the vertex/fragment shader, compute which tile a fragment belongs to
   and look up its highlight state. With a 4x4 grid this is trivial.
  - Overlay mesh (more flexible, later): Render a second transparent quad on top
   of highlighted tiles. More work but scales better and allows different visual
   effects.

  I'd start with the uniform approach. Your world shader already knows the
  vertex positions — you can derive tile index from floor(position.x) and
  floor(position.z).

  3. Engine: Expose to Lua

  Expose these C++ functions to Lua so game scripts can call them:
  - World.getHoveredTile() → returns tile x, y (or nil if cursor is off-world)
  - World.highlightTiles(tileList, color) → sets highlight state
  - World.clearHighlights() → resets

  4. Game (Lua): Movement logic

  -- In your player entity script or a MovementSystem script
  function onSelectEntity(entity)
      local tile = World.entityTile(entity)
      local range = entity.movementRange  -- from YAML or Lua config
      local reachable = World.getTilesInRadius(tile.x, tile.y, range)
      World.highlightTiles(reachable, {0.3, 0.5, 1.0, 0.4})  -- blue tint
  end

  function onTileHover(tileX, tileY)
      if isInReachableSet(tileX, tileY) then
          World.highlightTile(tileX, tileY, {1.0, 1.0, 1.0, 0.6})  -- white
      end
  end

  function onTileClick(tileX, tileY)
      if isInReachableSet(tileX, tileY) then
          entity:moveTo(tileX, tileY)
          World.clearHighlights()
      end
  end

  Why This Split?
  Concern: "Which tile is the mouse over?"
  Owner: Engine
  Reason: Requires raycasting, screen-space math, runs every frame —
    performance-sensitive
  ────────────────────────────────────────
  Concern: "How far can this unit move?"
  Owner: Game (Lua)
  Reason: Game rule, varies per unit type, will change with upgrades/buffs
  ────────────────────────────────────────
  Concern: "Which tiles are reachable?"
  Owner: Game (Lua)
  Reason: Game rule (later: terrain cost, obstacles, abilities)
  ────────────────────────────────────────
  Concern: "Render tile highlights"
  Owner: Engine
  Reason: GPU/shader work, needs to be fast
  ────────────────────────────────────────
  Concern: "Which tiles to highlight and in what color?"
  Owner: Game (Lua)
  Reason: Game decision (range = blue, hovered = white, enemy = red)
  ────────────────────────────────────────
  Concern: "What happens when I click a tile?"
  Owner: Game (Lua)
  Reason: Game logic (move, attack, interact)
  The Hover Question Specifically

  The hover detection (which tile is under the cursor) belongs to the engine.
  It's the same raycasting you already have, just snapped to a grid. But what to
   do with that information (highlight it? ignore it? show a tooltip?) is the
  game's decision via Lua.

  Think of it as: the engine is the nervous system (senses the world), Lua is
  the brain (decides what to do about it).

  Suggested Implementation Order

  1. Add worldPosToTile() to World — trivial math, immediate value
  2. Compute hovered tile every frame in the input path (extend the existing
  mouse callback)
  3. Add per-tile color support to the world shader (uniform array or SSBO)
  4. Expose tile query + highlight functions to Lua
  5. Write the movement range + hover logic in Lua
  6. Hook up click-to-move to use tile snapping instead of raw world positions

  This gives you incremental, testable progress and keeps the architecture clean
   for when you add pathfinding, terrain costs, and turn-based movement later.

● Good question. Let me be honest about where my proposal was solid, where it
  was hand-wavy, and where the effort/gain ratio actually matters for your
  project.

  What's Actually Fine As-Is

  The engine/game split — That's standard and correct. Engine owns spatial
  queries + rendering, game owns rules. Nothing to improve there.

  Starting with uniforms for tile highlights — For a 4x4 grid, this is the right
   call. Anyone suggesting SSBOs or texture lookups at this stage is
  over-engineering.

  The implementation order — Incremental, testable steps. That's just good
  practice.

  What I Got Wrong or Glossed Over

  1. Missing: State Machine for the Interaction Flow

  The problem: I described the flow as three disconnected callbacks
  (onSelectEntity, onTileHover, onTileClick). But XCOM-style movement is a state
   machine:

  IDLE → SELECTED → SHOWING_RANGE → HOVERING_TARGET → MOVING → IDLE

  Without this, you'll end up with scattered boolean flags and edge-case bugs
  (what if the player clicks empty space? right-clicks to cancel? selects a
  different entity mid-move?).

  Effort: Low. It's a design pattern, not heavy code. A Lua table with
  currentState and transition functions.
  Gain: High. Prevents spaghetti from day one. Every interaction feature you add
   later (attack, ability, cancel) slots cleanly into states.

  2. Per-Frame Lua Calls for Hover Are Wasteful

  The problem: I suggested the engine computes hovered tile, then calls Lua
  every frame to decide what to do. That's a Lua→C++ round-trip 60+ times per
  second for something that only changes when the mouse moves to a different
  tile.

  Better: Engine tracks hovered tile internally. Only calls into Lua when the
  hovered tile changes (event-driven). The engine can even handle the "is this
  tile in the highlighted set?" check itself — since it already holds the
  highlight data.

  Engine: tile changed from (2,3) to (2,4)
    → is (2,4) in highlight set? yes → update hover highlight (pure C++)
    → call Lua only on click or state transitions

  Effort: Low. You already have an observer pattern. Just add a "tile changed"
  event.
  Gain: Medium. Doesn't matter at 16 tiles, but it's the correct pattern and
  avoids building a bad habit into the architecture. More importantly, it keeps
  your Lua API simpler — fewer callbacks to implement.

  3. Missing: Tile Data Structure

  The problem: I treated tiles as pure coordinates. But even for your MVP, a
  tile should be a lightweight struct — at minimum knowing if it's
  valid/walkable. Right now your world is a flat height grid; there's no concept
   of "tile" as an addressable thing.

  Better: Either in World or as a parallel structure:
  struct Tile {
      int x, y;
      float height;
      bool walkable;       // for later
      // no pathfinding cost yet, no occupant yet
  };

  Effort: Very low. A few lines.
  Gain: Medium. Without it, you'll scatter tile-related data across multiple
  systems and regret it when you add obstacles or terrain types.

  4. Radius Computation: Lua Now, C++ Later

  The problem: I put "which tiles are reachable" in Lua. For a flat plane with
  Chebyshev distance, it's 5 lines of Lua and runs in microseconds. But once you
   add terrain costs and pathfinding, Lua becomes a bottleneck.

  Honest assessment: This is fine for now. Moving it to C++ later is
  straightforward — you'd replace a Lua function call with a C++ one behind the
  same API. The key is that your Lua API should be getReachableTiles(entityId, 
  range) not for each tile, check distance in Lua. If you design the API as a
  single call that returns results, swapping the implementation later is
  trivial.

  Effort to do it "right" now (C++): Medium, and premature.
  Effort to migrate later: Low, if the API boundary is clean.
  Gain from doing it in C++ now: Near zero. You have 16 tiles.

  5. I Didn't Address Your Existing PlayerControl System

  The problem: You already have PlayerControl doing click-to-move with raw world
   positions. My proposal didn't address how the new tile-based movement
  integrates with it. You'd either:

  - Extend PlayerControl to snap destinations to tile centers — minimal change,
  pragmatic
  - Create a new TileMovementSystem — cleaner separation, but more plumbing

  Honest take: Extend PlayerControl for now. You can refactor into a separate
  system when movement gets complex enough to justify it. Creating a new system
  now means wiring up a new system factory entry, Lua registration, entity
  assignment — overhead for no immediate benefit.

  Effort: Extending is very low. New system is medium.
  Gain from new system: Low right now. The abstraction isn't paying for itself
  yet.
